# Scheduled Jobs

Recurring background work is scheduled by **Hangfire** (SQL Server storage, `HangFire` schema — schedules survive restarts) and executed over **MassTransit**: each job is a one-line `IBus.Publish(...)` in [`RecurringJobRunner`](../ScoreTracker/ScoreTracker/HostedServices/RecurringJobRunner.cs), registered in [`Program.cs`](../ScoreTracker/ScoreTracker/Program.cs) via `RecurringJob.AddOrUpdate`. The published message is consumed by a saga inside the owning vertical.

All cron expressions are **UTC**.

| Job id | Cadence (UTC) | Message | Consumer (vertical) | What it does |
|---|---|---|---|---|
| `process-scores-tier-list` | Daily 07:00 | `ProcessScoresTiersListCommand` (per mix) | TierListSaga (ChartIntelligence) | Rebuilds the score-based tier lists per level (1–29) and chart type: groups all player scores, weights them by competitive-level delta, filters statistical outliers, persists the rankings. Fans out to Phoenix + Phoenix 2. |
| `calculate-scoring-difficulty` | Daily 08:00 | `RecalculateScoringDifficultyCommand` (per mix) | ScoringDifficultySaga (ChartIntelligence) | Recalculates each chart's scoring-difficulty level from weighted scores in a ±3-level window, normalized against chart level and player depth. Fans out to Phoenix + Phoenix 2. |
| `update-weekly-charts` | Daily 05:00 | `RotateWeeklyChartsCommand` (per mix) | WeeklyTournamentSaga (WeeklyChallenge) | Rotates the weekly challenge board **if the current week has expired**: writes placement history, clears the board, draws fresh charts (excluding recently used ones), sets next Monday's expiration (05:00 UTC = midnight ET on the EST reference). Early-exits while the week is still active — the daily cadence is a retry envelope, not the rotation period. Fans out to Phoenix + Phoenix 2 (parallel boards, like Daily Step); a mix with no catalog no-ops. (Moved from 09:00 back to 05:00 to restore the midnight-ET Monday reset the Hangfire extraction had pushed to 5am EDT.) |
| `rotate-daily-step` | Daily 05:00 | `RotateDailyStepCommand` (per mix) | DailyStepSaga (WeeklyChallenge) | Rotates the site-wide **Daily Step** board **if the day's board has expired**: snapshots the finishing placements to `UserDailyStepPlacing`, clears the board, draws one Singles/Doubles chart (level 16–24 normally; on the once-per-ISO-week **Limbo Day** it drops to level 1–15 and lowest-passing-score wins), and sets the next midnight-ET expiration. Fans out to Phoenix + Phoenix 2 (parallel boards); a mix with no catalog no-ops. 05:00 UTC = midnight ET on the EST reference. |
| `process-pumbility-tier-list` | Daily 10:30 | `ProcessPumbilityTierListCommand` (per mix) | TierListSaga (ChartIntelligence) | Rebuilds the PUMBILITY tier lists: prices every player's scores with the mix's own PUMBILITY formula, takes each top-50 pool per chart type, and counts how many of a cohort's pools hold each of a folder's charts. One row set per folder per cohort (P1 cohorts are difficulty title levels, P2 are PUMBILITY title rungs, plus an everyone cohort for the community view); a cohort whose pools reach nothing in a folder gets no rows. Fans out to Phoenix + Phoenix 2 — the full-pool gate keeps a mix with no real pools dark on its own. See [pumbility-tier-list.md](design/pumbility-tier-list.md). |
| `process-pass-tier-list` | Daily 09:30 | `ProcessPassTierListCommand` (per mix) | TierListSaga (ChartIntelligence) | Rebuilds the pass-count and PG tier lists for levels 10–29 across Singles, Doubles, and CoOp, weighting each player's passes by their competitive threshold. Fans out to Phoenix + Phoenix 2. |
| `calculate-chart-letter-difficulties` | Daily 10:00 | `RecalculateChartLetterDifficultiesCommand` (per mix) | ScoringDifficultySaga (ChartIntelligence) | Recalculates per-chart letter-grade (AA–PG) difficulty percentiles from the share of players meeting each grade threshold, weighted by competitive level. Fans out to Phoenix + Phoenix 2. |
| `recalculate-chart-similarity` | Daily 12:00 | `RecalculateChartSimilarityCommand` | ChartSimilaritySaga (ChartIntelligence) | Rebuilds the chart-similarity graph ([design](design/chart-similarity.md)): the top-20 nearest charts per chart on skill + intensity (same type, level ±1 and scoring level ±1.25, same-song excluded), persisted floor-free with the shared badges the shelf names each match from. **Order-independent** — it reads only the piucenter crawl (badge coverage + step analyses), so unlike its neighbours here it waits on nothing and its output moves only when the crawl does. **Phoenix-only** — the crawl it reads is Phoenix data (the one deliberate holdout in the Phoenix 2 note below). |
| `start-leaderboard-import` | Sundays 10:30 | `StartLeaderboardImportCommand` | LeaderboardSweepSaga (OfficialMirror) | Weekly sweep against the official PiuGame site writing one immutable snapshot: rating boards, chart boards (checkpointed per board), popularity, the two tier-list feeds, then the highlights/record-book stage — sealed at the end. The seal publishes `OfficialSnapshotSealedEvent`, which SupplementRollupSaga consumes to rebuild the supplemented reading ([supplemented-leaderboards.md](design/supplemented-leaderboards.md)) — a roll-up failure never blocks the official week. Only the seal makes the snapshot visible; a failed run records its stage+error for the `/Admin/OfficialLeaderboards` runs table (never a public page) while reads keep serving the last sealed snapshot. Sunsets when the Phoenix 1 site goes offline. |
| `start-phoenix2-leaderboard-import` | Sundays 16:30 | `StartLeaderboardImportCommand(Phoenix2)` | LeaderboardSweepSaga (OfficialMirror) | The Phoenix 2 twin of the row above, timed after the P2 pumbility board's daily 01:00 GMT+9 recompute. The P2 boards are login-gated: requires `PiuGame:ServiceUsername`/`ServicePassword` (a dedicated service account) or the import fails loudly naming those keys. Its rating boards are the daily PUMBILITY board's All/Singles/Doubles tabs (top 300 per chart board, walked page by page). |
| `try-schedule-mom` | Daily 11:00 | `TryScheduleMoMCommand` | MarchOfMurlocsHandler (EventCompetition) | Checks whether the latest March of Murlocs season has expired; schedules the next cycle (delayed message) or cycles immediately. Seasons are quarters ending 23:59:59 UTC-5 on the last day of March, June, September and December. Idempotent — defers if a future-dated MoM already exists. A cycle running late **catches up to the current quarter** rather than creating the quarter that follows the last season: an already-ended season leaves nothing future-dated to defer on, which is how this job once created a pair of seasons a day for 39 days ([march-of-murlocs.md](design/march-of-murlocs.md) §2.1). |
| `process-account-purges` | Daily 11:30 | `ProcessAccountPurgesCommand` | AccountPurgeSaga (Identity) | Purges accounts from two sources — retired accounts whose 30-day merge grace window ended, and self-serve deletions whose 7-day window ended ([delete-my-data.md](design/delete-my-data.md) §8): publishes `AccountPurgeStartedEvent` (every vertical deletes its own user-keyed rows, idempotently), deletes identity data, and drops the `User` row after a week of daily re-fires — the re-fire week is the in-memory-bus crash-safety mechanism. |
| `crawl-piucenter` | Mondays 06:00 | `CrawlPiuCenterCommand` | PiuCenterCrawlSaga (Catalog) | Weekly piucenter.com sync: reconciles the `ExternalChartAlias` map against their published chart table (new keys auto-match or park for admin resolution), fetches per-chart step-analysis JSON for charts missing the current data release (~1 req/s politeness throttle), banks the numbers in `ChartSkillMetric`, and regenerates the `ChartSkill` tags from them. Gap-driven — a near no-op unless piucenter shipped a new data release. Idempotent and resumable after restarts. |
| `purge-player-highlights` | Sundays 09:00 | `PurgePlayerHighlightsCommand` | PlayerHighlightPurgeConsumer (PlayerProgress) **and** CommunityHighlightPurgeConsumer (Communities) | Weekly purge of the significant-wins feed: deletes `scores.PlayerHighlight` payloads and the `scores.CommunityHighlight` audience-index rows over them, both older than 30 days (CH7 — home-page-widgets §7). One command with two consumers so the pair can't drift and leave an index pointing at wins that no longer exist. Idempotent, deletes by timestamp. |
| `retry-webhook-deliveries` | `*/5 * * * *` | Re-attempts community-tool webhook deliveries whose backoff has elapsed. The queue is a SQL table, so a delivery survives a restart; this is what picks it back up. |
| `flush-overdue-score-batches` | `*/5 * * * *` | `FlushOverdueScoreBatchesCommand` → `OverdueScoreBatchesFlushedEvent` | UpdatePhoenixRecordHandler (ScoreLedger) **then** RecoverInterruptedImportsConsumer (OfficialMirror) | Sweeps score work that should have announced itself and did not. The drain that ends a score batch is a scheduled message on the **in-memory** transport, so losing one strands everything derived from those scores — highlights, folder lamps, ratings, titles, the session card, the Discord post — behind an import that reported success, with no error anywhere. ScoreLedger takes every batch past its deadline plus `ScoreBatchPolicy.DrainBuffer` (atomically, via `TakeDueBatches`) and announces it, **then** publishes the event that starts the second half — the two are in scope for the same sessions, so running them concurrently double-announces. OfficialMirror then replays sessions that are stale (`StaleAfter`, 30 min — deliberately not `WorkExpectedWithin`, which is a reader's spinner) **and** show no drain (`NewCount`/`UpscoreCount` still zero, since `ProcessedAt` only lands when capture *finishes* and cannot tell "never drained" from "still capturing"). Capped at 25 sessions per pass, oldest first, deferral logged. Never closes a run — an unfinished one is either live or the boot pass's candidate. Also the `Flush Stuck Score Batches` button on `/Admin`, for when a player reports a silent import before the next tick ([import-restart-recovery.md](design/import-restart-recovery.md) §4.3). |
| `prune-webhook-deliveries` | `0 8 * * *` | Drops delivery bodies past 7 days and activity rows past 14. Two horizons: a body stops being useful once nobody can replay it, the log stays readable longer. |
| `reset-deep-scans` | `0 0 1 * *` | Refills every account's `User.DeepScansRemaining` to the monthly allowance (`DeepScanAllowanceHandlers.MonthlyAllowance`), so the Score check's full-account walks stay rationed. One `ExecuteUpdate` across the User table; an unused allowance does not roll over, and a hand-granted extra balance survives only until this fires. |

## Operational notes

- **Dashboard**: `/hangfire`, gated on admin (`HangfireDashboardAuthorization`). Use it to inspect, trigger, or retry jobs.
- **`PreventRecurringJobs=true`** (config flag) parks every job on a yearly Jan-1 cron (`0 0 1 1 *`) instead of its real cadence — so they stay visible in the `/hangfire` dashboard and can be run by hand with **Trigger now**, but never fire on their own. Set in environments that shouldn't run background work automatically (local dev, E2E).
- **Restart semantics**: schedules live in SQL and re-fire per Hangfire's misfire handling; but the MassTransit transport is **in-memory**, so a message that was mid-flight when the process died is gone. Jobs are designed to tolerate this (idempotent consumers, the flush job as a catch-up).
- **Adding a job** = one method on `RecurringJobRunner` + one `RecurringJob.AddOrUpdate` line in `Program.cs` + a consumer in the owning vertical. Do not introduce a second scheduler library or hosted-timer patterns.
- **Phoenix 2**: the compute-trigger messages (tier lists, scoring difficulty, weekly rotation, leaderboard import) carry a `MixEnum` defaulting to Phoenix. **Every compute job now fans out to both mixes** — the weekly and Daily Step rotations, the leaderboard imports, and (as of 2026-08-13, "Phoenix 2 tier lists are live") the scores, pass/PG, scoring-difficulty, letter-grade, and PUMBILITY tier-list jobs; each consumer's own thin-data guards keep a mix with little volume quiet rather than wrong. The one deliberate holdout is `recalculate-chart-similarity`, which reads the piucenter crawl — Phoenix data.
